# Комментарии к задачам: клиент API и состояние — шаг 9

Шаг 9 плана `workflow-service/docs/task-comments-plan.md`. Здесь клиент API комментариев и их состояние в приложении; экран — шаги 10–11. Правила API — в контракте `workflow-service/docs/task-comments-contract.md` и `docs/contracts/task-comments.openapi.yaml`.

## Модули

- `lib/api-errors.ts`, `lib/api.ts` — `request` возвращает прежнее сообщение `error` и в дополнение `status`, `code`, `details`, `retryAfterSeconds`, `aborted`. Прежние экраны читают только `error` и работают как раньше.
- `lib/task-comments/types.ts` — типы контракта.
- `lib/task-comments/errors.ts` — ошибка API в терминах экрана: вид, код, текст.
- `lib/task-comments/api.ts` — запросы, проверка формы ответов, таймаут, отмена.
- `lib/task-comments/feed.ts` — порядок ленты и склейка страниц.
- `lib/task-comments/store.ts` — ленты по задачам, неотправленные сообщения, правка и удаление.
- `lib/task-comments/mention-search.ts` — поиск кандидатов для @.
- `lib/task-comments/request-id.ts` — ключ повтора `client_request_id`, UUID v4.
- `lib/user-task-comments-api.ts`, `stores/task-comments-store.ts` — подключение к `request` и к учётной записи.
- `hooks/use-task-comments.ts` — хук карточки задачи.

Модули в `lib/task-comments` не зависят от React Native: API, сессия и таймеры передаются им снаружи, поэтому их проверяют тесты на Node.

## Ошибки

Экран различает, что случилось, по `failure.kind`:

| Вид | Когда | Что уже сделало состояние | Что показать |
|---|---|---|---|
| `offline` | Нет сети или сервер не ответил за 20 с | Сообщение осталось неотправленным с тем же ключом | «Нет соединения», повтор |
| `unavailable` | 404 `TASK_NOT_FOUND`: задачи нет или она больше не видна | Лента очищена, свои неотправленные остались | «Задача недоступна» |
| `read_only` | 403 `COMMENT_WRITE_FORBIDDEN` | `canComment = false`, лента перечитывается | Лента без поля ввода |
| `forbidden` | 403 `COMMENT_NOT_OWNED`, `MODULE_FORBIDDEN` | После правки или удаления лента перечитана | Сообщение сервера |
| `stale` | 409 `COMMENT_VERSION_CONFLICT`, `COMMENT_DELETED`, 404 `COMMENT_NOT_FOUND`, 400 `INVALID_CURSOR` | Лента перечитана; при `INVALID_CURSOR` — с самых новых | «Комментарий уже изменён», черновик не терять |
| `rejected` | 400 `VALIDATION_ERROR`, 409 `MENTION_NOT_AVAILABLE`, `IDEMPOTENCY_CONFLICT`, 413 | Сообщение осталось неотправленным | Исправить черновик, поля — в `details` (`mentions.2`) |
| `rate_limited` | 429 | — | Повтор через `retryAfterSeconds` |
| `unsupported` | 404 без кода: сервер не знает этого API | — | Скрыть комментарии |
| `server` | 5xx, ответ неожиданной формы | — | «Не удалось», повтор позже |
| `unauthenticated` | 401 | `request` вывел на экран входа, кэш очищен | — |
| `cancelled` | Запрос отменило приложение | — | Ничего |

Текст ошибки — серверный, если сервер прислал код; иначе свой: платформенное «Network request failed» или страница прокси пользователю ничего не скажут.

## Лента

- Открытие и возврат в карточку, возврат приложения из фона и свои изменения перечитывают ленту. Перечитывается всё загруженное — от самых новых до самого старого загруженного, по 100 за запрос. Иначе правки и удаления в уже загруженных страницах не были бы видны.
- История догружается по 30. В памяти — не больше 500 комментариев задачи: виртуализация списка экономит отрисовку, но не память, а обновление перечитывает всё загруженное. Дальше `historyLimited`, история не догружается.
- Если после многих новых комментариев обновление упёрлось в предел раньше, чем дошло до загруженного, более старые загруженные убираются: между ними и прочитанным мог остаться пропуск.
- Страницы склеиваются по ID, из двух версий комментария остаётся более новая: запоздалый ответ не откатит правку или удаление. При равной версии берётся пришедшая копия: права и имя автора меняются без новой версии.
- Порядок — время создания, затем ID. Сервер различает микросекунды, в ответе — миллисекунды, поэтому комментарии одной миллисекунды упорядочены по ID. Курсоры выдаёт сервер, на полноту ленты это не влияет.
- Одно чтение задачи за раз: повторное обновление ждёт идущего, обновление прерывает догрузку истории. Ответ прерванного или заменённого чтения не применяется, даже если сеть его не остановила.
- Ленты задач хранятся отдельно: ответ по одной задаче не попадает в другую. Закрытие карточки отменяет её чтение. Помнятся ленты 5 последних задач; открытая задача, задача с неотправленным сообщением или идущей правкой не забывается и сверх этого.

## Отправка

- Сообщение сразу видно как «отправляется» (`pending`) и получает ключ повтора. Сбой сети оставляет его «не отправленным» с тем же ключом: повтор (`retry`) не создаст копию, даже если первая попытка дошла.
- Повторное нажатие с тем же текстом не создаёт второе сообщение: пока идёт отправка, ждёт её ответа, после сбоя повторяет её с тем же ключом.
- Новый ключ — только после `IDEMPOTENCY_CONFLICT`: прежний занят другим содержимым.
- `discard` убирает неотправленное сообщение и возвращает его текст, чтобы вернуть в поле ввода.
- Закрытие карточки не отменяет отправку: отправленное не теряется.

## Правка и удаление

- По версии, которую видит экран. Ответ заменяет комментарий в ленте, удалённый остаётся на своём месте без текста.
- Изменения одного комментария идут по очереди. Повторное такое же нажатие ждёт идущего запроса. Другое действие — например, удаление во время сохранения правки — начинается после него, с новой версией.
- При `stale` лента перечитывается. Если нужное уже сделано — например, ответ на первую попытку потерялся, — это успех. Иначе конфликт остаётся ошибкой, черновик у экрана.

## Пользователь

Кэш принадлежит вошедшей учётной записи. Выход, вход другого пользователя и демо-режим отменяют все запросы и очищают всё. Ответы прежней сессии не применяются. В демо-режиме комментарии не запрашиваются: его токен сервер не принимает.

## Поиск кандидатов для @

Запрос уходит через 300 мс после последнего изменения. Прежний запрос отменяется, его ответ не применяется. Следующая страница — по курсору того же запроса, без повторов людей. Запрос длиннее 100 символов не отправляется: такого имени нет. Тот же запрос второй раз не отправляется, после ошибки — отправляется.

## Совместимость

- Другие экраны получают от `request` прежние сообщения — тест сверяет их с прежним выражением. Отменённый запрос больше не пишется в лог как ошибка сети; до этого шага отмены никто не использовал.
- Сервер без API комментариев отвечает 404 без кода — это `unsupported`, а не «задача недоступна».
- В TypeScript 6 типы `@types/node` больше не подключаются сами. Тесты исключены из `tsconfig.json` и проверяются отдельным `tsconfig.test.json`, поэтому типы Node не видны коду приложения.

## Проверки

`npm test` проверяет типы модуля и тестов (`tsc -p tsconfig.test.json`), затем запускает тесты `node:test` через `tsx`. Отдельная сборка не нужна. Локально на Node 20.20.2 и 25.8.1 — 60 тестов:

- `lib/__tests__/api-errors.test.ts` — прежние сообщения `request`, код, поля, `Retry-After`;
- `errors.test.ts` — вид каждого кода контракта, старый сервер, сеть, отмена;
- `api.test.ts` — запросы по контракту, только поля контракта в ответе и теле, таймаут, отмена, оборванный ответ;
- `feed.test.ts` — порядок, склейка по версии, перечитывание;
- `request-id.test.ts` — UUID v4, в том числе без `crypto` платформы;
- `store.test.ts` — 27 сценариев: запоздалые ответы, две задачи вперекрёст, закрытие карточки, смена пользователя, повтор с тем же ключом, двойное нажатие, конфликт версии и потерянный ответ, очередь изменений, «только чтение», потеря доступа, предел памяти, кэш задач;
- `mention-search.test.ts` — пауза, запоздалые ответы, страницы, закрытие.

Мутационные проверки роняют набор во всех 36 случаях, среди них: применяется запоздалый ответ; обновление не ждёт идущего; перечитывается одна страница; старая версия затирает новую; повтор с новым ключом; ответы прежнего пользователя; нет очереди изменений; потеря доступа оставляет ленту; «только чтение» оставляет поле ввода; поиск без паузы.

`npx tsc --noEmit` — только три прежние ошибки в `app/register/index.tsx`, `components/mood-check-in-card.tsx`, `components/requests/request-detail-ui.tsx`. ESLint по новым и изменённым файлам — без новых замечаний. `npm run lint` (`expo lint`) проверяет только `app`, `components`, `src` и до этого шага падал на 175 прежних замечаниях.

## Ограничения

- Интерфейс — шаги 10–11: список, поле ввода, выбор упоминаний, диапазоны при правке текста.
- Неотправленные сообщения живут, пока приложение запущено: после его закрытия их нет. Сообщение, которое успело дойти, появится при следующем обновлении.
- Повтор — только по действию пользователя, автоматического нет.
- Хук и ветка отмены в `request` тестами не покрыты: им нужен React Native. Хук проверяется на устройстве в шагах 10–11.
